# Hosted test environment (6 Nov 2026)

Supabase project `kingdom-connect-test` (ref `palsowodunzxqbbyenvb`, eu-central-1, free plan, test data only) and two Vercel projects on the personal team `light-8f71`: `kingdom-connect-member` (root `apps/member`) and `kingdom-connect-admin` (root `apps/admin`), both linked to `clainkavit/kingdom-connect` with git deployments disabled (deploy by hand).

- Secrets (DB password, service key, OTP and vault keys, seed password) live in the gitignored `.env.hosted` at the repo root. Nothing in git.
- Database: `supabase db push --linked`, then a seed copy with a random password and hosted vault values (the local `supabase/seed.sql` has the known local password and keys, never run it hosted). Legal texts: `pnpm legal:load` with `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. Functions: `supabase functions deploy --use-api`. Secrets: `OTP_SECRET`, `MAIL_FROM`, `MAIL_API_URL`; do not set `DB_URL` hosted, the built-in `SUPABASE_DB_URL` is used.
- Auth: the access token hook and site URL were pushed with `supabase config push` from a temporary folder holding only `[auth]`, so the local config.toml never overwrites the hosted one.
- Vercel deployment protection is on (Vercel login before any page).
- Login needs email: every sign-in sends an OTP through `MAIL_API_URL`, which sends through Brevo when the secret `BREVO_API_KEY` is set (F08, #46) and uses the Mailpit format otherwise. Without either secret, nobody can sign in on the hosted site except through the demo logins.
- Demo sign-in links: `EXPO_PUBLIC_DEMO_LINKS=1` (member) and `NEXT_PUBLIC_DEMO_LINKS=1` (admin) switch on `detectSessionInUrl`, set only on the two test Vercel projects. A link is `<site>/demo#t=<hashed_token>`, with `hashed_token` from the Auth admin `generate_link` call (type magiclink, service key from `.env.hosted`) for a seeded account such as `test.level2@example.test`. The page signs in only when the visitor presses Open the demo, because chat apps (WhatsApp seen on 6 Nov) fetch links for previews and a plain magic link is used up by that fetch. Each link works once. Never set these flags on a real environment.
- Vercel Authentication was switched off on both test projects on 6 Nov 2026 for a demo; the sites hold only fake people.
- Hosted-only extras, applied with `supabase db query --linked` and not in any migration: a trigger `private.demo_trust_test_accounts` on `auth.sessions` that marks sessions of `test.%@example.test` accounts as email-code verified, and terms and privacy acceptances for the six seeded members. Without them a demo link stops at the code screen and then the terms screen. Remove both before any real user is added to that project.
- Fake logins without the email code (6 Nov): the hosted project has the secret `DEMO_ACCOUNTS=1`, and the `login` function skips the email code for `test.<name>@example.test` accounts only when it is set (`skipsCode` in `supabase/functions/_shared/login-rules.ts`). Since 14 Nov 2026 (audit M1) it also needs `platform_settings.test_data_only` = `true` in the database, so the secret alone never skips the code on a real project. Members sign in with the username (`test_level1`, `test_level2`, `test_level3`), the admin with `test.admin@example.test`; the shared password is `DEMO_PASSWORD` in `.env.hosted`. Remove the secret, reset the passwords and delete the trigger and fake accounts before any real person is added.
- After every `supabase functions deploy`, run `supabase secrets unset DB_URL --project-ref <ref>`: the deploy re-applies the local config value (host `db`) and every function then fails with ENOTFOUND db.
- `supabase secrets set` run inside the repo folder does the same: on 9 Nov 2026 it overwrote the hosted `MAIL_FROM` with `noreply@example.test` (Brevo then rejected every login code) and `OTP_SECRET` with the public local value. Set secrets from an empty folder (the CLI binary is `node_modules/.bin/supabase`), or through the Composio Supabase tool, and compare `supabase secrets list` digests with the local values afterwards.
- Email (F08): sending goes through Brevo with the function secret `BREVO_API_KEY` (a key made for this only; Composio's Brevo connection uses another) and `MAIL_FROM=champion20041@gmail.com`, the one verified Brevo sender. A Gmail sender is for testing only; real members need an own domain with SPF and DKIM in Brevo. Brevo's authorised-IP blocking is off, because Edge Function addresses change.
